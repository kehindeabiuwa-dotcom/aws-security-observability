In my GuardDuty exercise, the finding described something specific: credentials intended for an EC2 instance role had been used from a remote AWS account. It included the affected resource, severity and finding type, giving me a starting point for investigation.

For this repository, the next task is to deliver findings to a notification channel. The repeatable test uses a sample finding, so it can check the route without repeating the vulnerable-application exercise.

---

## What We Are Building in This Part

An EventBridge rule receives GuardDuty findings, selects medium-or-higher severity events and forwards them to SNS. This is separate from the CloudTrail-to-CloudWatch path in the first two parts.

## Step 2 — Check Whether GuardDuty Is Already Enabled

```bash
aws guardduty list-detectors --region eu-west-2
```

If a detector already exists in the region, the stack's rule can receive its findings without owning or changing that detector.

If none exists, use the detector option on the initial lab deployment:

```bash
python3 scripts/deploy.py --region eu-west-2   --email you@example.com --create-detector
```

The script checks for an existing detector before creation. On updates, it preserves a detector already owned by the stack. This ownership matters later: cleanup removes a stack-owned detector but leaves pre-existing monitoring in place.

## Step 3 — Match the Event Type and Severity

The rule uses this event pattern:

```json
{
  "source": ["aws.guardduty"],
  "detail-type": ["GuardDuty Finding"],
  "detail": {
    "severity": [{"numeric": [">=", 4]}]
  }
}
```

That keeps lower-severity findings out of this notification path. It is a lab threshold to understand and test, not a claim that lower-severity findings are unimportant.

The target is the lab SNS topic. Its policy allows EventBridge to publish there. The CloudWatch alarm permission is configured separately.

---

## Step 4 — Send a Sample Through the Path

```bash
python3 scripts/test_security.py guardduty --region eu-west-2
```

The script requests a sample `Backdoor:EC2/DenialOfService.Tcp` finding. Verify the `[SAMPLE]` label, the EventBridge invocation and the received SNS message. Keep the sample classification in the evidence.

A delivered sample confirms event filtering and notification routing. It does not prove that GuardDuty detected a new attack in the account.

---

## Troubleshooting: The Finding Exists, but No Email Arrives

Check the region and severity first. Then inspect whether the rule is enabled, its invocation and failed-invocation metrics, the SNS topic policy and the subscription confirmation.

Do not change the secret-read alarm while investigating this path: the GuardDuty event does not pass through that alarm. The architecture diagram helps keep those responsibilities separate.

---

## What I Learned

The finding supplies context; EventBridge decides which events to route; SNS delivers the notification. Keeping those responsibilities explicit makes failures easier to locate.

The vulnerable application, malware-protection exercise and automated containment workflow in my broader notes are outside this repository's baseline. They would need their own deployment and verification steps.
